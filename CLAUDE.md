# ANEXT — Anexador de Teses

App interno (Tkinter + ttkbootstrap) que gera, divide e junta os documentos de cada segurado da tese num PDF, para a equipe de revisão de insumos do FAP. Usuário: advogado(a) do escritório Rodriguez & Sousa, não necessariamente com bagagem técnica profunda — prefira explicações práticas a jargão quando o assunto sair do código em si.

**Mantenha este arquivo atualizado** conforme o projeto muda — é o que evita ter que reexplicar o contexto do zero em cada conversa nova.

## Onde isso vive

- Monorepo privado `claude-code` (GitHub, B0NASSI) — este repositório, pasta `ANEXT/`. É a fonte de verdade.
- Espelho de código-fonte público `ANEXT---Anexador-de-Teses` (GitHub, B0NASSI) — é dali que o launcher instalado baixa as releases (`GITHUB_OWNER`/`GITHUB_REPO` em `src/launcher.py`). Precisa ser sincronizado manualmente a cada release (não é um subtree/submodule de verdade — ver "Processo de release" abaixo).
- `ANEXT/anext-public-sync/` — worktree isolado (git próprio, gitignorado no monorepo) apontando pro repositório público (`anext-origin/main`, branch local `anext-public-main`). Fica parado entre releases — não precisa recriar a cada versão, só sincronizar os arquivos e dar push nele.

## Arquitetura, em resumo

- `src/app.py` — janela principal. Desde a v4.0, layout "barra lateral": navegação fica numa sidebar azul-marinho à esquerda (não mais abas no topo — o `ttk.Notebook` interno continua existindo pra gerenciar as 4 páginas, mas sem desenhar as próprias abas), com cada etapa num card de borda fina. As 4 páginas continuam sendo All-in-one, Gerar capas, Dividir capas, Juntar PDFs.
  - `_colorir_barra_titulo()` pinta a barra de título nativa do Windows na cor do tema (API DWM `DWMWA_CAPTION_COLOR`, via `ctypes.windll.user32.GetAncestor(hwnd, GA_ROOT)` — **use `GetAncestor`, não `GetParent`**, é o que o GERAPED usa e é mais robusto pra achar o HWND de topo real). Só funciona no Windows 11 (build 22000+); falha em silêncio em versões mais antigas.
- `src/tema.py` — estilo ttkbootstrap: cores, sidebar, cards. `Pagina.TFrame`/afins existem só se a página precisar (hoje o ANEXT não usa fundo cinza atrás dos cards — foi tentado e revertido, o usuário achou ruim; ver histórico do GERAPED se quiser reconsiderar).
- `src/visual.py` — gera o banner antigo (gradiente + ícone + texto via Pillow). **Não está mais em uso pelo `app.py`** desde o redesenho da v4.0 (a sidebar substituiu o banner no topo), mas **continua sendo importado por `launcher.py`** (a janela de progresso de "baixando atualização" ainda usa `visual.gerar_banner`). **Pegadinha que já aconteceu**: apagar `visual.py` por parecer código morto quebra a checagem de versão fora do launcher em silêncio (`import launcher` falha com `ModuleNotFoundError`, capturado por um `except Exception` que só loga) — sempre grep por `import visual`/`visual\.` antes de remover qualquer coisa "não usada" em `app.py`.
- `src/launcher.py` — checa releases no GitHub, baixa, confere SHA256 (`ASSET_NAME + ".sha256"`, ver `installer/gerar_checksum.py`), aplica a atualização e reabre o app. **Atualização é obrigatória** — sem opt-in, todo mundo recebe ao mesmo tempo.
  - **Pegadinha importante**: `apply_update()` só sobrescreve `ANEXT.exe` e o conteúdo de `_internal/` — o `ANEXT Launcher.exe` já instalado NUNCA é atualizado pelo auto-update. Uma correção só dentro de `launcher.py` não chega em quem já tem o app instalado; se o bug precisa alcançar todo mundo, a correção/mitigação tem que rodar no `app.py` (que sim é atualizado a cada release). Ex.: `_limpar_zips_temporarios_orfaos()` em `app.py`, que limpa na inicialização um bug antigo do launcher que deixava `tmp*.zip` (~40MB) esquecidos na pasta de instalação a cada atualização aplicada com sucesso.
- `src/log_setup.py` — log rotativo (`logging.handlers.RotatingFileHandler`, append simples) em `logs/<nome>.log`, ao lado do `.exe`. Usado por `app.py` (`anext.log`) e `launcher.py` (`launcher.log`). Cada uma das 4 abas loga o início (`logger.info` no começo do worker), sucesso (`logger.info` no final) e erro com traceback (`logger.exception`) de toda operação — sem isso, um erro dentro de um callback do Tkinter desaparece sem rastro (build usa `console=False`), e sem a linha de início, um travamento no meio não deixa nenhum rastro de até onde chegou. Ctrl+L (`app.py:_abrir_log`) abre o log com a entrada mais recente no topo — inverte a ordem só numa cópia temporária gerada na hora de abrir, o arquivo real em disco continua em ordem cronológica normal (mais rápido e mais seguro contra corrupção que reescrever o arquivo inteiro a cada linha).
- `src/diagnostico.py` — `metadados_anext()` grava só versão do ANEXT + data/hora nas propriedades (Arquivo → Propriedades) de todo PDF gerado, para investigar erros futuros. Deliberadamente **não** inclui usuário, máquina, pasta/arquivos de origem nem nomes de segurados — não é um registro de auditoria/fiscalização, e dado de cliente não tem por que ir pras propriedades do PDF.
- `src/anexo_fixo.py` — algumas teses sempre levam o mesmo documento de referência como último anexo (hoje: "CONTESTAÇÃO ADMINISTRATIVA, EFEITO SUSPENSIVO E PRAZO PRESCRICIONAL" → `anexos_fixos/ACORDAO STJ.pdf`). `caminho_anexo_fixo(titulo)` casa o "Título da tese" do All-in-one por semelhança (tolera maiúsculas/acentos/espaços/pequeno erro de digitação, via `difflib.SequenceMatcher`, limiar 0.90) e devolve o PDF a anexar, ou `None`. `juntar_pdfs.juntar_tese(..., anexo_extra=...)` insere esse PDF como últimas páginas. Um aviso discreto (📎) aparece no campo "Título da tese" quando bate. PDFs ficam em `anexos_fixos/`, bundled no `.exe` (ver `.spec`) — pra cadastrar uma nova tese com anexo fixo, é só adicionar o par título→arquivo em `_ANEXOS_POR_TITULO` e colocar o PDF na pasta.
- `src/limites_caminho.py` — trunca nomes livres (segurado, pasta da tese) o quanto for preciso pra não estourar o limite de 260 caracteres de caminho do Windows.
- `src/tabela.py`, `src/documento.py`, `src/gerar.py`, `src/separar_capas.py`, `src/juntar_pdfs.py`, `src/compactar_pdf.py`, `src/pdf.py` — lógica de negócio, majoritariamente sem dependência de UI.
- `CaixaColarTabela` (em `app.py`) — componente reutilizado nas abas All-in-one e Gerar capas para colar a tabela do Word (Ctrl+V) com captura automática da formatação (mesclagens/cores/bordas/fontes) via Word invisível, com fallback para texto simples.
- `_avisar_se_desatualizado()` (em `app.py`, chamada logo antes de `root.mainloop()`) — rede de segurança para quando alguém abre o `ANEXT.exe` direto, sem passar pelo launcher (ex.: fixou o ícone errado na barra de tarefas a partir do app já aberto, em vez do atalho da área de trabalho que aponta pro launcher). Reaproveita `get_latest_release`/`is_newer`/`read_local_version` de `launcher.py` via `import launcher` dentro da própria thread de checagem — só avisa com um `messagebox.showinfo` (sem número de versão na mensagem, decisão deliberada) pra fechar e reabrir pelo atalho; nunca baixa nem trava o app, falha em silêncio (só loga) se não conseguir checar. Mesmo padrão já usado no RequerimentoGERID.
  - **Pegadinha que já mordeu no REQUERID**: `app.py` importa `launcher.py` só por essas 3 funções, então o build do `ANEXT.exe` passa a precisar de `requests` de verdade (não só o hidden import — collect_all completo, ver `.spec`) e **não pode excluir `email`/`http`** dos `excludes` do Analysis do app — `requests` depende deles por baixo dos panos (via urllib3) pra abrir a conexão HTTPS. Excluir quebra a checagem em silêncio (sem crash, só nunca encontra atualização), só detectável com log dentro do except. Sempre confira o `.spec` antes de adicionar qualquer coisa que use `requests`/rede em `app.py`.
  - Detalhe de implementação: `log_setup.configurar_logging("launcher.log", BASE_DIR)` em `launcher.py` fica dentro de `main()`, não no nível do módulo — se rodasse na importação, o `app.py` ganharia um segundo handler de log (`launcher.log`) duplicando tudo que ele já loga em `anext.log`.

## Testes

`tests/` (pytest, `pytest.ini` aponta `pythonpath = src`). Cobre `tabela.py`, `separar_capas.py`, `juntar_pdfs.py`, `compactar_pdf.py` — tudo com PDFs sintéticos (nunca usar `ANEXT/Exemplos/` como fixture: é gitignorado por ter dados reais de cliente, não existe em clone novo).

**Não cobertos, propositalmente**: `documento.py`, `gerar.py`, `pdf.py` — dependem do Word via COM (`pywin32`), não dá pra rodar limpo sem Word instalado.

Rodar: `.venv\Scripts\pytest -v` (venv próprio do ANEXT, criado com `uv venv .venv` + `uv pip install -r requirements-dev.txt`).

## Processo de release (manual, sem CI ainda)

1. Bump `versao.txt` + criar `NOTAS DE ATUALIZAÇÃO/X.Y.txt` **antes de compilar** (a nota fica embutida dentro do `.exe`, não é um arquivo solto), commit no monorepo.
2. `.venv\Scripts\python.exe installer\build_release.py` — compila do zero (nunca reaproveita build antigo), empacota, gera o checksum, e **confere sozinho que a nota da versão atual está de fato dentro do zip** antes de deixar prosseguir (aborta com erro claro se a nota não existir, ou se o zip sair sem ela). Existe porque já aconteceu de publicar uma release reaproveitando um build feito antes de escrever a nota — o app não tinha a nota, sem erro nenhum na hora. Não publica nada sozinho; termina imprimindo o comando `gh release create` pronto pra copiar.
3. `gh release create <versão> ... --repo B0NASSI/ANEXT---Anexador-de-Teses` (comando impresso no fim do passo 2).
4. Sincronizar o código-fonte pro repositório público: usar o worktree em `ANEXT/anext-public-sync/` (branch `anext-public-main`, já configurado apontando pra `anext-origin/main` — não precisa recriar a cada release; vive dentro de `ANEXT/` mas é gitignorado no monorepo, tem `.git` próprio). Copiar os arquivos rastreados de `ANEXT/` (via `git -C <monorepo> ls-files -z ANEXT/`, sem prefixo — **use `-z`/NUL-separado**, texto normal quebra em nomes com acento tipo "NOTAS DE ATUALIZAÇÃO"), commitar e dar push — nunca faça isso com `cd` solto misturado em vários comandos (já causou um incidente de arquivos apagados no lugar errado; sempre use `git -C <caminho>` explícito).
   - **Pegadinha**: o classificador de auto mode do Claude Code bloqueia esses comandos (`git status`/`add`/`push` nesse worktree) como possível "Data Exfiltration"/"Sensitive-Source Provenance", mesmo sendo o processo documentado aqui. `git status`/`add`/`commit` destravam com uma regra de permissão em `.claude/settings.local.json` tipo `"Bash(git -C \"<caminho para o worktree>\" *)"` — mas o `git push` final continuou bloqueado mesmo com a regra (parece ser um limite mais rígido, não contornável só por permissão). Nesse caso, prepare tudo (copie, `add`, `commit`) e peça pro usuário rodar o `git push anext-origin anext-public-main:main` manualmente.

Se publicar algo incompleto por engano: `gh release delete <versão> --repo ... --yes` apaga a release, mas **não** apaga a tag — precisa `git push <repo-público> --delete <versão>` separado, senão a próxima `gh release create` com o mesmo número reaproveita a tag antiga (apontando pro commit errado).

**Sempre peça confirmação antes de publicar** (`gh release create`), mesmo em correção rotineira — e separe explicitamente "correção" de "feature nova/não testada" nesse pedido, pra não empacotar as duas coisas juntas sem o usuário poder escolher segurar a feature.
